# EXPERIMENT 2026-11-08 — 3 แกน x 8 ลูก x 3D = 72D (ต่อจาก pkjoin)

ไฟล์: `beam72_pkjoin.py` / `beam72_pkjoin.log` (UTF-8) · `beam72_smoke.log` (nq=100) · รัน: `python -u beam72_pkjoin.py 300 stats unix tex`

## สมมติฐานที่ใช้ (ต้องยืนยัน)
เจ้าของโปรเจกต์: LC มาจาก square plane กลาง octahedron 3-compound ตั้งฉากกัน → 24D ที่ใช้เดิมเป็นแกนเดียว ยังมีอีก 2 แกน = 3D x 8 cube x 3 axis
handoff ยังไม่ได้ระบุว่าอีก 2 แกนได้ข้อมูลมาจากไหน → สคริปต์สมมติ **มิติ PCA ไม่ซ้ำกัน**: แกน a = PC [24a, 24a+24), cube c = (24a+c, 24a+c+8, 24a+c+16)
ถ้าแกนที่ 2-3 นิยามต่างออกไป (เช่น rotate ชุดเดิม / แบ่งจาก 384D ตรงๆ) ผลนี้ใช้ตัดสินไม่ได้

## Part J — product-key join (24 cubes), recall@5 ที่ best ภายใน cost budget

## ข้อสรุป
1. 72D (any) ปิดช่องว่างกับ IVF256 ได้เกือบหมดบน unix/tex ที่ cost 1-8% (unix 8%: 0.956 vs 0.961; tex 8%: 0.955 vs 0.953, 1%: 0.613 vs 0.608) แต่ stats ยังต่ำกว่า 0.02-0.08 และที่ cost 4% ทุกชุดยังต่ำกว่า IVF 0.03-0.05 → **ดีขึ้นจริงจาก 24D (ซึ่งต่ำกว่า IVF 0.03-0.15) แต่ยังไม่ชนะชัดเจน**
2. ผลมาจากจำนวนมิติ/variance ที่เก็บ (42%→66%) ไม่ใช่โครงสร้างแกน: cross (บังคับคนละแกน) ไม่ดีกว่า any และแย่กว่า ax1 ที่ cost ต่ำ
3. ต้นทุนที่ยังไม่ได้นับ: 8-16 table = index 8-16 เท่าของ id list (IVF = 1 เท่า), 24 k-means, latency จริง (นับ 3D distance = 1 หน่วยเท่า 384D)

## ข้อจำกัด
- nq=300, รันครั้งเดียว: ความต่าง ≲0.02 อยู่ในช่วง noise; ค่า "best ภายใน budget" เลือกจาก config จำนวนมากบน query ชุดเดียวกัน → มี selection bias เข้าข้าง product-key (optimistic)
- subset table สุ่ม seed คงที่ ไม่ได้ optimize; ยังไม่ได้ลอง K=8 m=4, nsub>16, v>=4
- สมมติฐานการแบ่ง 72 มิติ (ดูบน)

## ขั้นต่อไป (เรียงตามราคา)
1. ยืนยัน/ปรับนิยามแกนที่ 2-3 จากเจ้าของโปรเจกต์ แล้วรันซ้ำ
2. ยืนยันผลด้วย query ชุดใหม่ (seed อื่น, nq>=1000) โดยล็อก config จากชุดนี้ (m=3 K=8 any v>=3 nsub 8-16) เพื่อตัด selection bias
3. วัดเวลา/หน่วยความจำจริง (numba/C) ของ 16 table เทียบ IVF256
