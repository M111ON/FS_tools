# Soft zone bias vs the hard zone filter (2026-10-26)

Card `task-tabbd47c5`. `scope:"zone:N"` has always been a **filter**: it
replaces the walk with the zone's rows, so an answer outside the zone cannot be
returned. The soft arm keeps the route and only **adds** `bias` to the score of
rows in that zone — the same contract graft's cluster bias has. Until now nobody
had put the two arms side by side.

## Contract

```
POST /v1/state/search {"vec":[…],"topk":5,"scope":"zone:2","bias":0.01}
```

- `bias` is read only when the scope resolves to a **zone** (a file/kind scope
  with 40 rows would just be a wider filter). On any other scope it is ignored,
  so it can never silently widen a tag filter into a global search.
- Clamped to `[0, 0.5]`. Cosine gaps between real neighbours are 0.01–0.05; a
  larger nudge would drown the geometry, and 0.5 is already a very strong pull.
- `bias` absent or 0 = the old behaviour, byte-identical (same hits, same
  `walk_hash`, same `items_scored`). The mode label is `soft+zone`.
- The walk is **not** touched: same buckets, same totem latch, same order
  sidecar. A soft request therefore cannot hide work — its cost equals the
  global arm's, which is exactly the number the mini-vector-DB card
  (`task-t4fbea5cf`) has to cut.

## Measured (live index, 63,837 rows, 60 real query rows, top-5)

One scratch server on the live index + tag sidecar, all arms in the same moment
(`bench_soft_zone.py --port 8098 --queries 60`). "keep global" = share of the
unscoped top-5 that the arm still returns; "in-zone" = share of returned rows
that belong to the query's zone.

| arm | keep global | in-zone | items_scored | latency p50 |
|---|---|---|---|---|
| global | 1.000 | 0.607 | 16,712 | 13.5 ms |
| hard `zone:2` | **0.603** | 1.000 | 13,197 | 8.8 ms |
| soft `0.005` | 0.947 | 0.660 | 16,712 | 14.0 ms |
| soft `0.010` | 0.910 | 0.697 | 16,712 | 14.1 ms |
| soft `0.020` | 0.877 | 0.730 | 16,712 | 13.7 ms |
| soft `0.050` | **0.743** | 0.863 | 16,712 | 14.2 ms |

Reading it:

1. The hard filter costs **40% of the global answer** (0.603). That is the
   honest price of "narrower question on purpose" — not a bug, but it must be
   quoted as a loss, never as a win.
2. A small nudge (0.005) costs almost nothing (0.947 kept) and still moves the
   zone share from 0.607 to 0.660.
3. The knob is monotone: 0.05 buys 0.863 in-zone while still keeping 74% of the
   global answer — the region where a soft pull is strictly more informative
   than the hard filter.
4. Work: the soft arm scores exactly the global arm's rows. In **this** index
   the hard filter's saving is only 21% (16,712 → 13,197) because the large
   zones (v1-migrate 21k, chatpool 14k) are most of the budget anyway; the
   saving is real only for small zones (architecture 334 rows → ~50x).

So the honest conclusion: soft bias is the right default for "I am searching in
my zone but I still want the true global answer"; the hard filter stays for
"only this zone may answer" (small zones, known query intent). Neither cuts the
walk — the work cut is the next card.

## Verification

`tests/test_soft_zone.py` (9 checks, in `run_tests.py`) builds a 30-row scratch
index with one deliberate **bridge row**: a zone-2 row that is close enough to
the zone-0 query to be a global top-5 answer.

| check | proves |
|---|---|
| S1 | `bias:0` is the plain search — same hits, `walk_hash`, `items_scored` |
| S2 | the hard filter cannot return the bridge row (by construction) |
| S3 | soft keeps it and is labelled `soft+zone` |
| S4 | the soft walk hash and work equal the global walk's |
| S5 | `bias:99` is clamped, not rejected |
| S6 | `bias` on a file scope stays a filter |
