### 3.1 tick / chunk คืออะไร

log ยาว ๆ ถูกตัดเป็นช่วงละ **8 บรรทัด = 1 tick** โดยนับ **ลำดับการเขียน** ไม่ใช่นาฬิกา
ข้อดี: เขียนเพิ่มเท่าไร เลข tick เดิมก็ไม่เปลี่ยน และตรงกับที่แถบ slide ในหน้าธรรมชาติ (ระนาบ) ใช้

- **หัวข้อ tick** (แถบเดียว) = `tick 12 · บรรทัด 96–103 · 14:17 – 14:54 · 8 บรรทัด` + ชิปว่าใครเขียนบ้าง
- กดหัว tick = กาง/พับ — tick เก่าพับไว้ให้อ่านภาพรวมยาว ๆ ได้เร็ว (มีปุ่ม **กาง**/**พับ** ทุก tick)
- แถบ **tick 0–4** กลางจอ = ลากไปหา tick นั้นได้ตรง ๆ (ปุ่ม ◀ ▶ เลื่อนทีละ tick)
- การ์ดที่ข้อความยาวจะถูกย่อไว้ กด **“อ่านต่อ”** เพื่อเปิดเต็ม
- ตัวเลขบนแถบ tick บอกตรง ๆ ว่ากำลังดู **กี่บรรทัดล่าสุดที่โหลด** (ยังไม่โหลดย้อนหลังเกินรั้น)

## 13. 🧹 curator — ซ่อนข้อความไร้สาระ/เทสต์สัญญาณ

ปุ่ม **🧹** บนหัวจอ (เปิดไว้เป็นค่าเริ่มต้น) จะซ่อนบรรทัดที่ "ไม่ใช่ข้อความจริง" ออกจาก feed เช่น `test` · `ping` · `ok` · `ครับ` · `ses_xxxx` · บรรทัดซ้ำๆ · สัญญาณรบกวนแบบ `======`

- **log ไม่ถูกแตะเลย** — curator ซ่อนเฉพาะบนจอ (แสดงผล) ทุกบรรทัดยังอยู่ครบในไฟล์และยังค้นเจอได้
- แต่ละช่วง **tick** ที่มีของถูกซ่อนจะมีป้าย **🧹 n** — กดป้ายนั้นเพื่อดู/ซ่อนเฉพาะ tick นั้น
- บรรทัดที่กดดูจะขึ้นแบบจางๆ พร้อมบอกว่า **ซ่อนเพราะกฎอะไร คะแนนเท่าไหร่**
- แผง ☰ มีส่วน **CURATOR** บอกว่าโหลดกี่บรรทัด ซ่อนกี่บรรทัด กฎไหนยิงเท่าไหร่ และยกตัวอย่างที่ซ่อนไว้
- **สิ่งที่ไม่ถูกซ่อนเด็ดขาด**: DM (ส่งถึงคนเดียว) · ข้อความที่มี @mention · บรรทัด bond/pointer/code · ข้อความยาวหรือหลายบรรทัด · บรรทัดที่มีคำสำคัญ (HANDOFF / DECISION / CORRECT...)
- กด **🧹** อีกครั้ง = ปิด เห็นทุกบรรทัด (รวมเทสต์สัญญาณ) เหมือนเดิม

ดูรายงานแบบบรรทัดคำสั่ง (ไม่ต้องเปิดเบราว์เซอร์):

```bash

python I:\tools\chat-pool\pool.py curate --clean      # ดู feed ฉบับที่กรองแล้ว
python I:\tools\chat-pool\pool.py curate --json       # เอาไปใช้ต่อเป็นข้อมูล

```

### 13.1 prune — ตัดเทสต์/สัญญาณออกจาก "ระนาบ" จริงๆ

**ซ่อน** กับ **prune** เป็นคำถามเดียวกันคนละผลลัพธ์:

| | ซ่อน (feed) | prune (ระนาบ) |
|---|---|---|
| บรรทัดยังอยู่ไหม | อยู่ครบ เห็นได้กดดู | อยู่ครบเหมือนกัน |
| ต่างกันตรงไหน | ไม่แสดงบน feed | **ไม่กินที่อยู่** → เซลล์ที่อยู่ได้ด้วย noise ล้วนหายจากระนาบ |
| ปุ่ม | 🧹 บนหัวจอ | **🧹 prune** ในแถบระนาบ |

กติกาใช้**ชุดเดียวกัน** กับ curator — ต่างกันแค่ปลายทาง:

| กฎ | จับอะไร | ตัวอย่างที่ถูกตัด |
|---|---|---|
| `test-word` | บรรทัดที่เป็นคำเทสต์ล้วน | `test` · `ping` · `hello` · `foo` |
| `test-probe` | รูป `test: ...` / `probe=...` | `test: smoke` |
| `stub` | ≤3 ตัวอักษร ไม่มีเนื้อหา | `...` · บรรทัดว่าง (heartbeat) |
| `ack` | คำรับทราบสั้นๆ | `ok` · `y` · `ครับ` · `รับทราบ` |
| `sess-id` | token เครื่อง | `ses_a1b2c3…` |
| `hex-blob` / `b64-blob` | blob ยาวๆ ไม่มีคำ | 32+ hex เปล่าๆ |
| `punct-soup` | ไม่มีตัวอักษร/เลขเลย | `=====` |
| `loud` | อักขระเดิมซ้ำ 8+ ครั้งในบรรทัดสั้น | `!!!!!!!!` |
| `repeat` | ข้อความเดิมซ้ำภายใน 20 บรรทัด | ฉบับที่ 2 เป็นต้นไป (ฉบับแรกเก็บไว้) |

**ไม่ถูก prune เด็ดขาด** (กฎป้องกัน — ตรวจรูปทรงก่อนคำ):

| กันด้วย | เพราะ |
|---|---|
| `kind` | bond / pointer / block ถือกราฟไว้ ไม่ใช่คำพูด |
| `dm` | ส่งถึงคนเดียว = เรื่องของคนนั้น |
| `mention` | มี `@ชื่อ` = มีคนต้องลงมือ |
| `long` | ยาวเกิน 240 ตัวอักษร หรือหลายบรรทัด = เนื้อหาจริง |
| `marker` | มี HANDOFF / DECISION / SESSION / สรุป / มติ |

> **หมายเหตุ**: `kind` เทียบแบบไม่สนตัวพิมพ์ใหญ่เล็ก — `CHAT` กับ `chat` เป็นชนิดเดียวกัน ถ้าเทียบตรงตัวจะทําให้ทุกบรรทัดของ platform ที่ส่ง `CHAT` ถูก "ป้องกัน" จน curator ปิดทั้งระบบ

ดูตัวเลขจริงและกติกาที่ตัดจริง (ไม่ต้องเปิดเบราว์เซอร์):

```bash
python I:\tools\chat-pool\pool.py prune              # ระนาบตัดไปกี่บรรทัด กฎไหนบ้าง + ตัวอย่าง
python I:\tools\chat-pool\pool.py prune --reveal     # เปิดโชว์บรรทัดที่ถูกตัด
python I:\tools\chat-pool\pool.py prune --json       # เอาไปใช้ต่อ
set POOL_CURATOR_PRUNE=3 && python I:\tools\chat-pool\pool.py prune   # ตัดเข้มขึ้น (เก็บทุกกรณีที่คะแนน 2)
```

ทาง HTTP: `GET /curator?prune=1` ได้ทั้งรายงาน hide + prune + สถิติระนาบ

#### prune ไม่ได้หยุดที่แผนที่ — มันไปถึงเส้นด้วย

การลบบรรทัดออกจากระนาบไม่ใช่เรื่องของแผนที่อย่างเดียว **bond** และ **sighting** เป็นสิ่งที่ *อ้างที่อยู่* ถ้าปลายทางถูกตัด เส้นนั้นก็ไม่ควรถูกวาดอีก แต่ตัวเส้นเองยังสมบูรณ์ (kind ถูกป้องกัน) จึงต้องแยกให้ออกระหว่าง "เส้นเดิมยังอยู่" กับ "เส้นนี้ยังชี้ไปที่ที่มองเห็นได้"

กติกาเดียวกันกับเซลล์: **ตัดโดยปริยาย, เปิดได้เสมอ**

| ชั้น | เกิดอะไรเมื่อปลายทางถูกตัด | `?raw=1` |
|---|---|---|
| bond (`/bonds`) | ไม่ถูกวาด — ประทับ `dangling: true` | คืนทุกเส้นพร้อมธง |
| sighting (`/pointers`) | ไม่ถูกวาด — ประทับ `dangling: true` | คืนทุกอันพร้อมธง |
| memory link (`/ctx/links`) | ไม่ถูกวาด — ประทับ `dangling: true` | คืนทุกเส้นพร้อมธง |

สิ่งที่ต้องรู้เพิ่ม 2 อย่าง:

- **นับแล้วบอกในคำตอบ** — `/ctx/links` มี `total` กับ `dangling` มาด้วยเสมอ ลูกข่ายไม่ต้องยิง 2 ครั้งมาเทียบเองเพื่อรู้ว่ามีอะไรถูกซ่อน
- **sighting นับ "การอ่านล่าสุดต่อแอป"** — อ่าน 4 ครั้งจากแอปเดียวเหลืออันล่าสุดอันเดียว ถ้าต้องการเห็นหลายอันพร้อมกันต้องใช้คนละชื่อแอป (นี่คือเจตนา ไม่ใช่ข้อจำกัด)

ดูยอดรวมได้ที่แผง CURATOR ส่วน *▦ ระนาบ — prune จริง* — จะขึ้นบรรทัด `🪢 ชี้ไปที่ที่ถูกตัด: bond N · pointer M`

#### ตรวจว่าระนาบ "ตัดจริง" ไม่ใช่ "ซ่อนบนจอ"

```bash
python I:\tools\chat-pool\prune_check.py    # 9/9 PASS — ยิง HTTP จริงเข้า server จริง
```

`prune_check.py` สร้าง sandbox ที่มี noise ตั้งใจ เปิด server ตัวจริงแล้วถามคำถามที่ตอบไม่ได้จากข้อมูลจริง (คลังของคุณสะอาด — prune ได้ 0 บรรทัด จึงไม่มีอะไรให้ทดสอบ): ปลายทางที่ถูกตัดหายจากคำตอบปกติไหม · `raw=1` คืนมันพร้อมธง `dangling` ไหม · การอ่านที่ชี้ไปที่ที่ยังสดอยู่ถูกใส่ธงผิดไหม · และคำถามข้ามระบบยังตอบได้ไหมตอน index ยังไม่ถูกสร้าง

## 14. ▦ ระนาบ (visualizer) — ดูข้อมูลทั้งก้อน

- **สี = ชั้นข้อมูล** เลือกได้ 4 แบบ: *จำนวนบรรทัด* · *heat (อัดด้วย √ ให้หางยาวอ่านออก)* · *ใครเขียนล่าสุด* (สี = แอป) · *ล่าสุดเมื่อไร* (น้ำเงิน=เก่า → แดง=ใหม่) — ชั้น who/when จะโหลดตอนเลือกครั้งแรกเท่านั้น
- **แถบ tick ด้านบน** = หนึ่งแท่งคือหนึ่งช่วง 8 บรรทัด (chunk เดียวกับ feed) สูงตามจำนวนบรรทัด สีตามคนที่เขียนมากสุด — **ลากแถบเพื่อเลื่อนเวลา**
- **hub เด่น** 3 อันแรกมีกรอบทอง — จุดที่ข้อมูลหนักสุด
- **วงฟ้า ◌ = มีคนประกาศว่าอ่านตรงนั้น** (sighting) — วงที่คงขนาดเป็นพิกเซล ไม่หดตามซูม จึงเห็นได้แม้ตอนทั้งระนาบ 144×144 ย่อในมือถือ · **กดช่อง = ประกาศการอ่าน** อัตโนมัติ (ดูกติกาด้านล่าง)
- **ขีดจำกัดของเส้น** — ระนาบเลือก **hub N** เองได้ (12/30/60/120) ว่าให้กี่จุดถือเป็น hub แล้วลากเส้นของจุดนั้น เลข 12 ตั้งไว้ตอนระนาบมีเส้นไม่กี่สิบเส้น พอมีเส้นเป็นหมื่น **เพดานนี้เองคือสิ่งที่ซ่อนเส้น ไม่ใช่วิธีวาด** — hub 12 = 209 เส้น, hub 60 = 807 เส้น
- **รัศมี 1/2/3 hop** = บังทุกอย่างที่ไม่เกี่ยวกับจุดที่เลือก
- **▶ replay** เล่นระนาบค่อยๆ ติดทีละบรรทัด · **←/→** เลื่อนทีละ tick · **space** เล่น/หยุด · **Esc** ปิด
- **▢ หน้าต่าง = viewport** เลือกขนาด 12/24/36/48/72 เซลล์ แล้ว **ลาก** หรือ **Shift+ลูกศร** เพื่อเลื่อน · หน้าต่าง **วนรอบ torus** — เลื่อนผ่าน x=143 แล้วโผล่ที่ 0 (ขอบเดียวกัน) ภาพไม่กระโดด เพราะ `pvWrap()` ตัวเดียวใช้ทั้งวางเซลล์/เลื่อนกรอบ/คลิก
- **⤓ png** บันทึกภาพระนาบเป็นไฟล์ PNG
- กดช่อง = เปิด pointer ที่จุดนั้น (อ่านของจริงตรงจุดนั้น ไม่มี state ค้าง) · ช่องที่แน่นเกิน budget จะแตกชั้นให้อ่านต่อ

## 15. ▣ ก้อนเรื่องราว · วิธีการ — ความจำที่ทุก platform อ่านตรงกัน

feed เก็บว่าใคร **พูด** อะไร · bond เก็บว่าอะไร **เชื่อม** กับอะไร · **ก้อน** เก็บว่าเรา **เรียนรู้** อะไร — เรื่องราวของงานหนึ่งชิ้น + วิธีการที่ทำให้เกิดมัน + หลักฐานที่ตรวจซ้ำได้ ส่วนนี้คือรากฐานที่ทุก platform (opencode · hermes · freebuff · codebuddy · codex) อ่าน text เดียวกันแล้วเข้าใจตรงกัน

- กดปุ่ม **▣ ก้อน** บนหัวจอ → การ์ดขึ้น **เหนือ chatbox** (มือถือแนวตั้งอ่านได้ ไม่ต้องเลื่อนข้าง)
- การ์ดตอนปิด = slug · rev · สถานะ · ใครร่วม · เวลา · addr/tick + ชื่อเรื่อง → **กดที่การ์ด** เพื่อกาง `story / method / evidence / refs`
- ในกางมี **ประวัติ rev** — ทุกครั้งที่แก้จะเพิ่มเป็นบรรทัดใหม่ ของเก่าไม่หาย (ประวัติคือเชนนั่นเอง)
- ช่องค้นหา = ค้นในเรื่องราว+วิธีการ (Enter) · เลือกสถานะได้ `open / closed / parked`
- **ก้อนไม่ถูก curator ซ่อน** เด็ดขาด (การป้องกันตาม kind) และเห็นใน feed เป็นบรรทัดเดียว `app/block ▣ slug revN · สถานะ: เรื่อง`

เขียนก้อนใหม่ (ทุก platform วิธีเดียวกันหมด — เลือกอย่างใดอย่างหนึ่ง):

```bash
# 1) ทาง CLI — บอกได้ครบทุกช่อง
python I:\tools\chat-pool\pool.py block av-window-view --as freebuff \
  --title "อ่าน .tess เป็นหน้าต่าง 144x144 แบบ page-aligned" \
  --story "...เกิดอะไรขึ้น ทำไมสำคัญ..." \
  --method "1) ... 2) ... 3) ..." \
  --evidence "ตัวเลข/ไฟล์/เทสต์" --refs 3fc8579d --status closed

# 2) ทาง HTTP (ใช้ได้จากทุก platform)
POST /block {"app":"freebuff","slug":"...","title":"...","story":"...",
              "method":"...","evidence":"...","refs":"3fc8579d","status":"closed"}
```

อ่าน / ตรวจ:

```bash
python I:\tools\chat-pool\pool.py blocks                     # ทั้งหมด (การ์ดความกว้างคงที่)
python I:\tools\chat-pool\pool.py blocks --q measure          # ค้น

```

- `refs` = 8 ตัวแรกของ hash บรรทัดต้นทาง → `block-show` จะบอกว่า **refs: 1/1 resolve กับเชน** (อ้างหลักฐานที่เชนไม่คลุมไม่ได้)
- `slug` = ที่อยู่ของก้อน ใช้ซ้ำเดิมเสมอเมื่อแก้ · `rev` = 1, 2, 3 …
- ก้อนถูกนับเป็นบรรทัดปกติ: มี rkey/enc อยู่บนระนาบ 144×144 กดดูจากระนาบได้ด้วย
- ค่าในช่องเป็น **บรรทัดเดียว** เสมอ (ขึ้นบรรทัดใหม่จะถูกย่อเป็นช่องว่าง — กันฟอร์แมตพัง)

## 16. ⏱ timeline — ดูว่า platform ไหนปิดงานเมื่อไร

กดปุ่ม **⏱ timeline** บนหัวจอ → แผงแนวตั้งแสดง session-block ทุกก้อนเรียงตามเวลา (เก่าบน → ใหม่ล่าง)

- **จุดสีฟ้า** = block ปกติ · **จุดสีส้ม** = block ที่มีคู่ dedup (เกี่ยวข้องกับ block อื่น)
- **ลูกศร ↗** ในการ์ด = link ไปยัง block ที่มีความคล้ายคลึง (similarity ≥ 40%) → กดเพื่อข้ามไปดู
- ข้อมูลจาก `GET /blocks/timeline` → server คำนวณ dedup links ด้วย weighted Jaccard (title 3x weight)
- รีเฟรชอัตโนมัติทุก 30 วินาที

## 17. ⚡ Auto-block — ปิด session → เขียนก้อนอัตโนมัติ

ทุก platform ไม่ต้องเขียนก้อนเอง — เรียก 1 บรรทัดตอนเริ่มงาน แล้วตอนปิด process ก้อนจะถูกเขียนอัตโนมัติ

```python
import pool
pool.register_app("freebuff")
pool.pool_session_guard("freebuff")   # ← แค่นี้ ปิด process = เขียนก้อน
```

กติกาอัตโนมัติ:
- ≥ 3 บรรทัด + ≥ 1 บรรทัดสาระ → เขียนก้อน
- < 3 บรรทัด หรือไม่มีสาระ → ข้าม (ไม่สร้างก้อนว่าง)
- ก้อนซ้ำ (title similarity ≥ 40% ภายใน 1 ชม.) → bump rev แทน slug ใหม่
- `force=True` → บังคับเขียนแม้ session สั้น

**platform ที่มี guard แล้ว**: pool-server (server เอง), hermes (via MCP server)
platform อื่นแค่เพิ่ม `pool_session_guard("app-name")` ใน startup

| กันซ้ำ | `(src, rel, dst)` ที่มีอยู่แล้วถูกข้าม → รันซ้ำไม่ทบ | `sighting_once()` — อ่านที่เดิมซ้ำไม่เขียนใหม่ |

**ทำไม sighting ต้องมาจากการอ่านเท่านั้น** — ระบบมี `record=True` มาตั้งแต่ต้น แต่ **ไม่มีใครเรียกเลย** ระนาบจึงมี 0 วงตลอดมา ตอนนี้กดช่องบนระนาบ = ประกาศว่าอ่านตรงนั้น (วงขึ้นทันที ไม่รอ poll รอบถัดไป) ถ้าคุณแค่ต้องการเห็นวงโดยไม่อยากกด ก็รอไม่ได้ — **มันคือบันทึกว่าใครดูตรงไหน ปลอมไม่ได้**

## 20. เมื่อระนาบจะเต็ม 20,736 — เกิดอะไรขึ้น และใช้ยังไง

คำตอบสั้น: **จำนวนเซลล์ไม่ใช่กำแพง — แต่มีกำแพงจริงอยู่ในกลไกที่ควรรับมือมัน**

### 1. การ "แตะ" เซลล์ใหม่ช้ามาก ไม่ใช่กำแพง

ตอนนี้ 25,230 บรรทัด → แตะ 10,118 เซลล์ (48.8%) และความชันกำลังแบน: จาก 12,000 → 25,230 บรรทัด (**เพิ่มกว่าสองเท่า**) ได้เซลล์ใหม่เพิ่มแค่ 1,447

ถ้าแฮชกระจายสม่ำเสมอเท่ากัน: **90% ต้อง ~47,700 บรรทัด · 99% ต้อง ~95,500** แต่ของจริงวิ่งต่ำกว่าแบบสม่ำเสมอ ~30% เพราะ RDH แมพข้องความคล้ายไปที่อยู่ใกล้กัน — **ต้องใช้มากกว่านั้นอีก**

### 2. กำแพงจริงคือ "ความหลากหลาย" ไม่ใช่จำนวน

ระนาบแตะ 49% แต่ **ใช้ไปแล้ว 81%** ถ้าวัดด้วยความหลากหลายจริง (`1/Σp²`):

| ชนิด | บรรทัด | เซลล์ที่แตะ | เซลล์ที่มีผลจริง | แน่นสุด |
|---|---|---|---|---|
| bond | 13,572 | 2,651 | **1,407** | 32 |
| chat | 6,631 | 5,070 | 3,749 | 13 |
| decision | 5,025 | 4,451 | 4,018 | 4 |
| **รวม** | 25,230 | 10,118 | **3,848 (18.6%)** | 34 |

**bond แย่ที่สุด** — 13,572 บรรทัดรูปร่าง `<64hex> <rel> <64hex>` ตกลงใน 2,651 เซลล์ เพราะข้องความคล้ายกันมาก็อยู่ที่เดียวกัน **นี่คือคุณสมบัติของ RDH ไม่ใช่บัก** — มันคือสิ่งที่ทำให้ "ค้นด้วยที่อยู่" ทำงาน

### 3. ลิ้นระบายของล้นถูกอุด — และตอนนี้อุดแล้ว

ตาม §5.4 เซลล์ที่แน่นเกินจะ **ซ้อนชั้น**: รับได้ 144^d × 64 บรรทัดโดยระนาบไม่โต **แต่กลไกนี้ทำงานไม่ได้เลย** เพราะ `_axis(line, depth)` ดันให้ค่าเดิมทุกความลึก:

- การแสกนอ่าน `data[(i + phase) % len(data)]` → พอข้อความ **≥ 48 ไบต์ จะเดินทุกไบต์ครบพอดีหนึ่งรอบ** → `phase` แค่ **สลับลำดับ ไม่เปลี่ยนผลรวม**
- บรรทัดจริงทุกบรรทัดยาวเกิน 48 ไบต์ → **ไม่มีบรรทัดไหนกดซ้อนชั้นได้เลย**
- วัตจริง: เซลล์ที่มี 132 บรรทัด ตอบ **132/1 ที่ depth 1, 2, 3 เท่ากันหมด** `still_over` ค้างที่ 1 → **เปิดไม่ได้ตลอดกาล**

**เพราะเซลล์หนึ่งเก็บบรรทัดที่ "ผลรวมชนกัน" — ฟังก์ชันใดๆ ของผลรวมเดียวกันจึงแยกมันไม่ได้ ไม่ว่าที่ phase ไหน** แกนย่อยจึงต้องใช้สิ่งที่ผลรวมทิ้งไป: **ตำแหน่ง**

| | ก่อน | หลัง |
|---|---|---|
| `_axis` ต่างกันตาม depth | 0/400 บรรทัด | **400/400** |
| เซลล์ 132 บรรทัดที่ depth 1 | 1 ช่อง, max 132, ค้าง | **9 ช่อง, max 29, `still_over` 0** |
| เซลล์จริง 1614 (34 บรรทัด) | 24 ช่อง, max 24 | **29 ช่อง, max 2** |

**ข้อจำกัดที่ยังเหลือ:** นี่คือการ **กระจาย** ไม่ใช่แฮชสม่ำเสมอสมบูรณ์ 400 บรรทัดที่ต่างกันแค่ตัวเลขต่อท้าย ยังลง max 40 ต่อช่อง (เทียบของจริง max 2) — ข้อความที่คล้ายกันมากยังชนกัน นี่คือคุณสมบัติของข้อง แต่มันพอแล้วที่ **เซลล์ที่ล้นเกินเปิดได้ในขั้นเดียว**

### 4. แล้วต้องทำอะไรเมื่อใกล้เต็ม

| เมื่อไหร่ | สัญญาณ | ทำอะไร |
|---|---|---|
| ระนาบจุดเริ่มจาง (สีเดียวกันหมด) | เปลี่ยนไปใช้สีแบบ **heat** หรือ **ล่าสุดเมื่อไร** — จำนวนเซลล์ไม่บอกอะไรแล้ว แต่ความหนาแน่นยังบอก | |
| เซลล์แน่นเกิน 64 | เปิดช่องนั้น → ระนาบขึ้นปุ่ม **↑ ขึ้นชั้น** → กดลงชั้นไปเรื่อยๆ | หลังแก้แล้วลงชั้นได้จริง |
| อยากได้ที่อยู่ใหม่จริงๆ | — | **เพิ่มของจริง** ไม่มีทางลัด: ที่อยู่มาจาก (เนื้อหา, แอป) ถ้าข้อความคล้ายกัน มันจะไปที่เดิม |

**อย่าเปลี่ยน RDH scale** — `RDH_CAPTURE_SCALE` จะเลื่อนที่อยู่ทุกอันที่มีอยู่ = ระนาบที่แชร์กันพังทันที นี่คือเหตุผลที่การล้นแก้ด้วย "ซ้อนชั้น" ไม่ใช่ "ขยายระนาบ"

## 21. ทำไมระนาบโหลดเส้นแบบ lean

ระนาบโหลดเส้นใหม่ทุกครั้งที่เปิด — ที่ 10,641 เส้น payload เต็มคือ **4.1 MB** ต่อครั้ง ซึ่งหนักเกินไปสำหรับมือถือ ระนาบจึงขอแบบ `?fields=plane` ที่ตัด 64-hex ของหัว-ท้ายออก (ระนาบรู้ที่อยู่ของเส้นจาก **เซลล์** ที่ปลายทั้งสองอยู่ ไม่ได้อ่าน hash เต็ม) → **2.6 MB (ลด 38%)** โดยรูปข้อมูลที่ JS เห็นไม่เปลี่ยน

## 22. 🧭 เดินเรื่อง — อะไรไปเกี่ยวกับอะไร และอะไรอ้างถึงมัน

ระนาบตอบคำถาม *"ของอยู่ตรงไหน"* แต่พอไปยืนตรงนั้นแล้ว คำถามถัดไปที่คนถามจริงคือ **"แล้วมันไปเกี่ยวกับอะไรบ้าง"** — สองคำถามนี้ต้องการข้อมูลชุดเดียวกัน (bond) แต่มุมคนละด้าน

**วิธีใช้:** เปิดระนาบ → คลิกช่อง → แผงขวาขึ้นรูปทรงของที่อยู่นั้น → กดปุ่ม **🧭** ที่บรรทัดไหนก็ได้ เพื่อเดินตามบรรทัดนั้น

### รูปทรง 5 แบบ

รูปทรงคือคำกล่าวอ้างเกี่ยวกับ **ทั้งภาพรอบจุด** จึงต้องใช้ *ทั้ง* สองทิศ:

| ทรง | อ่านว่า | สภาวะ |
|---|---|---|
| **○ เกาะ** | ไม่มีเส้นเลย — ยังไม่มีอะไรอ้างถึง และมันไม่อ้างใคร | ออก 0 · เข้า 0 |
| **▶ ต้นน้ำ** | ไปข้างหน้าได้ แต่ไม่มีใครชี้กลับ | ออก > 0 · เข้า 0 |
| **◀ ปลายน้ำ** | มีคนอ้างถึง แต่ต่อจากนี้ไม่มีอะไรออก | ออก 0 · เข้า > 0 |
| **⇄ กลางสาย** | มีทั้งก่อนหน้าและต่อจากนี้ — ช่วงกลางของเรื่อง | ออก > 0 · เข้า > 0 |
| **— เส้นเชื่อม** | บรรทัดนี้คือ *เส้น* เอง ไม่ใช่ปลายทาง | `kind="bond"` |

**แถวสุดท้ายคัญกว่าที่คิด** — ในคลังนี้มี **13,572 บรรทัด** ที่เป็น bond ถ้าเอามันไปนับเป็นเกาะเพราะ "ไม่มีเส้นของมันเอง" เท่านั้นจะกลายเป็นว่า **ครึ่งคลังไม่มีอะไรเชื่อมเลย** ซึ่งตรงข้ามกับความจริงทั้งหมด — มันคือตัวเชื่อมเอง แผงจึงแยกมันออกเป็นถังของตัวเอง และตัวเลขทุกถังรวมกัน = จำนวนบรรทัดทั้งหมดเสมอ

### 🌟 ชุมทาง ≠ ปลายน้ำ

รูปทรงคือ **เรขาคณิต** ส่วนชุมทางคือ **น้ำหนัก** — บรรทัดที่ถูกอ้างถึง 1 ครั้ง กับ 273 ครั้ง มีรูปทรงเดียวกัน (◀) แต่เป็นของที่ต่างกันโดยสิ้นเชิงในแง่ที่ต้องรู้ แผงจึงบอก **in 273 · ข้าม platform 273 · 🌟 ชุมทาง** — ไม่ยุบสองอย่างนี้เข้าด้วยกัน

### เดินต่อและรอยเท้า

กดที่บรรทัดปลายทาง (หรือกดที่ hop ใดๆ) = **เดินไปที่นั้น** ทั้งระนาบจะย้ายตาม (เพราะรูปทรงเป็นคำกล่าวอ้างเรื่องที่อยู่ ถ้าแผนที่ค้างอยู่ที่เดิม แผงกับระนาบจะขัดกัน) ด้านบนมี **รอยเท้า** ให้กดย้อนกลับได้ทุกจุด

รอยเท้า **ไม่ถูกบันทึกลง pool** — sighting บอกว่า "มีคนอ่านตรงนี้" ซึ่งเป็นข้อเท็จจริง ส่วนรอยเท้าบอกว่า "ผมหลงตรงนี้" ซึ่งไม่ใช่ และถ้าบันทึก มันจะท่วม sighting จริง

### 📊 แพทเทิน — รูปทรงของทั้งระนาบ

ปุ่มในแถบระนาบ เปิดแผงที่บอกว่าระนาบทั้งใบมีอะไรบ้าง:

```

—  เส้นเชื่อม  54%
⇄  กลางสาย   25%
○  เกาะ       12%
▶  ต้นน้ำ      6%
◀  ปลายน้ำ      3%
```

และ **แยกตามคนเขียน** ซึ่งเปิดเผยสิ่งที่มองจากช่องใดช่องหนึ่งไม่มีทางเห็น:

| platform | บรรทัด | เกาะ | เกาะกี่ % |
|---|---|---|---|
| **opencode** | 6,072 | 253 | **4%** |
| **hermes** | 5,056 | 2,637 | **52%** |
| dashboard | 524 | 107 | 22% |
| index | 0 | 0 | — (เขียน 13,572 เส้น) |

**opencode เกือบทั้งหมดถูกเชื่อม แต่ hermes เกินครึ่งเป็นเกาะ** — เพราะ session ของ opencode ต่อเป็นแถว (`x-next-in-session`) และบรรทัดของมันถูกพ่วงไปหานิยามของ hermes (`x-uses-term`) ส่วน hermes เองเป็น **ปลายน้ำ**: เป็นนิยามที่คนอื่นอ้างถึง แต่นิยามด้วยกันเองไม่ได้ต่อกัน

มีตาราง **ชุมทาง** ให้ด้วย — บรรทัดที่มีคนอ้างถึงตั้งแต่ 5 ขึ้นไป กดเข้าไปเดินต่อได้เลย นี่คือรายการสิ่งที่ทุกอย่างเกาะอยู่ และมันมีไม่กี่บรรทัด

## 23. API ของชั้นสำรวจ

```bash
curl "http://127.0.0.1:8390/explore?rkey=1599&hops=2"     # เดินจาก “ที่อยู่” (ช่องที่คลิก)
curl "http://127.0.0.1:8390/explore?hash=<64hex>&hops=2"  # เดินจาก “บรรทัด”
curl "http://127.0.0.1:8390/patterns"                     # รูปทรงของระนาบทั้งใบ
```

| พารามิเตอร์ | ความหมาย | ค่า |
|---|---|---|
| `?hash=` | เดินจากบรรทัดเดียว (64-hex หรือคำนำหน้า) | — |
| `?rkey=` | เดินจากที่อยู่ (ช่องที่กำลังเปิด) | 0–20735 |
| `&hops=` | เดินกี่ช่วง | 1–4 (ตามหลัก 2) |
| `&cap=` | แสดงกี่บรรทัดต่อช่วง | 1–60 (ตามหลัก 14) |

ทั้งสองตอบรูปเดียวกัน: `shape` (รูปทรง + หลักฐาน) · `in`/`out` (แต่ละช่วงพร้อม `total` และ `nodes`) · แต่ละ node มี `in`/`out` ของตัวเองมาด้วย จึงจัดอันดับต่อได้โดยไม่ต้องถามรอบใหม่

`?rkey=` ตอบเพิ่มอีกสองอย่างที่ `?hash=` ไม่มี เพราะ **ที่อยู่** ยกคำถามที่บรรทัดเดียวถามไม่ได้: `shapes` (รูปทรงของ *ทุก* บรรทัดที่อยู่ข้างใน — ช่องที่มีแค่แชท 5 บรรทัด กับช่องที่มีนิยามที่ทั้งคลังอ้างถึง ดูเหมือนกันเป๊ะถ้านับเป็น "5 บรรทัด") และ `lines` (รายการบรรทัดในช่องนั้นพร้อมดีกรีของแต่ละบรรทัด)

**ทำไม `cap` ต้องมี** — ชุมทาง `ctd` มี **273 เส้น** ชี้เข้ามา ส่งทั้งหมดคือส่งกำแพงข้อความที่อ่านไม่ได้ `_hop_nodes` จึงจัดอันดับด้วยดีกรีของปลายทาง (จุดที่ไปต่อได้ ยิ่งน่าสนใจ) แล้วบอก `total` ตามจริง — **“แสดง 14 จาก 273” ซื่อสัตย์กว่า “14”**

### ราคา

ชั้นนี้เพิ่ม pass หนึ่งรอบ (`_brief()` — 0.40s ที่ 25k บรรทัด) ต่อการ append หนึ่งครั้ง แล้ว **cache จนกว่า log จะเปลี่ยน** หลังจากนั้น `reach` 1 ms · `explore_cell` 53 ms · `pattern_census` 50 ms

### จุดตัดของแว่นคือ “ที่อยู่” ไม่ใช่ “บริเวณ”

แว่นต้องมี**จุด** ไม่ใช่แค่พื้นที่ ไม่งั้นคำถาม "กำลังดูอะไรอยู่" ไม่มีคำตอบ เส้นเล็งเขียน ✛ ไว้ที่จุดนั้น และอัปเดตทุกครั้งที่ลาก

### ⛔ ขยายได้ถึง “สเกลจริง” เท่านั้น — แล้วมันบอกว่ามีอะไรอยู่

**ขอบเขตของแว่นคือความละเอียดของข้อมูล ไม่ใช่ความสวยงาม** ที่อยู่ที่เล็กที่สุดคือ *1 เซลล์* ดังนั้นขีดจำกัดคือจุดที่ 1 เซลล์เต็มแว่น (`2r / ขนาดเซลล์`) แว่นจะหยุดตรงนั้นแล้วเขียน **จำนวนบรรทัดของที่อยู่นั้น** แทน — เพราะการซูมต่อจากจุดนั้นคือการย่อตัวเลขเดียวให้ใหญ​่ ไม่ใช่ข้อมูลใหม่

ระดับที่แถบสถานะบอก คือ **ความละเอียดจริง** ไม่ใช่ตัวคูณ — `×4` บนจอใหญ่คือ "บล็อก" บนจอมือถือ คือ "เซลล์" ระดับบอกเฉยๆ จึงหมายถึงอย่างเดียวกันบนทุกจอ

| ระดับ | เกณฑ์ | หมายความว่า |
|---|---|---|
| **L2 ระนาบ** | เซลล์ < 3px | ยังเป็นแผนที่ความหนาแน่น — ยังแยกเซลล์ไม่ออก |
| **L1 บล็อก** | 3–7px | เห็นกริด 12×12 — ที่อยู่ยังรวมกันอยู่ |
| **L0 เซลล์** | 7px ขึ้นไป | แต่ละช่องแยกออกจากกัน ตัวเลขคือข้อมูล |
| **จริง** | 1 ช่องเต็มแว่น | หยุด — ต่อจากนี้มีแต่เนื้อใน |

### แว่นก็วนรอบ torus

วางแว่นไว้ใกล้ขอบระนาบแล้วขอบแว่นจะไปโพล่ดอีกฝั่ง **เพราะมันคือแว่นเดิม ไม่ใช่แว่นใหม่** — การวางเนื้อหาทั้งหมดคำนวณเป็นระยะทางตาม torus จึงไม่มี logic ขอบให้เขียนเลย

### ทำไมโหมดหน้าต่าง ไม่ใช่ L2 ทั้งระนาบ

แว่นมีรัศมี จึงวางตรงกลางไม่ได้ใกล้ขอบเกินกว่า `r` เซลล์ — บนระนาบ 144×144 เต็ม มันจะกัน **~25 วง** ออกไปอย่างถาวร หน้าต่าง 48×48 จึงเป็นที่ให้แว่นเคลื่อนได้ โดยการลากพื้นยังเข้าไม่ถึงที่หมายได้ทุกจุด — ไม่มีที่ไหนเข้าไม่ถึงเลย มีแค่ยังไม่อยู่ในกรอบ

### กรอบแคนวาสที่เคยย่อค้าง — แก้แล้ว

ก่อนหน้านี้กรอบแคนวาสเป็น `flex:0 0 auto` ทำให้ `pstep()` อ่านความสูง **ของตัวเอง** เพื่อกำหนดขนาดกล่องที่มันอยู่ข้างใน — วนกันเอง แว่นหรือแถบเครื่องมือเพิ่มมาหนึ่งแถว แคนวาสก็หดลง**แบบค้าง** (เจอจริง: 156px) ตอนนี้ทั้งสองครึ่งใช้ `min-height:0` และกล่องแคนวาส `overflow:hidden` — ความสูงจริงทุกเฟรม ทุกเฟรมจึงตกลงตรงกัน

## 25. ขา input — ส่งไม่ผ่านแล้วข้อความต้องไม่หาย

### ข้อความที่พิมพ์ไว้จะถูกลบก็ต่อเมื่อเข้าสายโซ่แล้ว

ก่อนหน้านี้ `send()` ล้างช่องข้อความ**ก่อน**ที่คำขอจะเสร็จ ผลคือถ้าเซิร์ฟเวอร์ไม่ตอบ — กำลังรีสตาร์ท, มือถือหลุด LAN, token ถูกปฏิเสธ — ข้อความที่พิมพ์ไว้**หายทันที** และ**ไม่มีข้อความแจ้งอะไรเลย**

วัดจริงตอน `fetch` ล้มเหลว:

```
ก่อน:  ช่องว่างเปล่า · ไม่มี toast · unhandledrejection = ["Failed to fetch"]
หลัง:  ข้อความยังอยู่ในช่อง
       toast "ส่งไม่ถึงเซิร์ฟเวอร์ — ข้อความยังอยู่ในช่อง (กด Enter อีกครั้ง)"
```

กติกาตอนนี้: **ล้างช่องเฉพาะใน `if(r.ok)`** — คือตอนที่บรรทัดอยู่ในเชนแล้วเท่านั้น ข้อความที่ส่งไม่ผ่านกู้คืนได้ ข้อความที่ถูกลบกู้คืนไม่ได้

### ส่งซ้ำ / ส่งค้าง — กันแล้ว

| เดิม | ตอนนี้ |
|---|---|
| กด Enter รัว = กันซ้ำได้เพราะล้างช่องทันที (ซึ่งคือการแลกที่ทำให้ข้อความหาย) | มีธง `sending` — 3 ครั้งรัว = `/append` **1 ครั้ง** |
| `fetch` ล้ม = เงียบ ไม่มีอะไรขึ้น | toast + ข้อความยังอยู่ในช่อง + โฟกัสกลับให้กด Enter ซ้ำ |
| ปุ่มส่งกดซ้ำได้ระหว่างรอ | ปุ่ม **disable ระหว่างส่ง** |

### เซิร์ฟเวอร์ตอบทุกครั้ง แม้ body จะพัง

```
POST /append '{bad json'   →  ก่อน: http=000 (ไม่ตอบเลย)
                              ตอนนี้: 400 {"error":"body must be a JSON object"}
```

`http=000` แยกไม่ออกจาก "เซิร์ฟเวอร์ตาย" — ฝั่งที่เขียนต้อง **ปฏิเสธให้ดัง** ไม่ใช่เงียบ และข้อความ error ต้องบอก**สาเหตุจริง** ไม่ใช่ชี้ไปที่ทะเบียนแอป

### token ผิด ไม่วนเงียบอีกแล้ว

`EventSource` ไม่บอก**สาเหตุ**ที่ล้ม จึงแยกไม่ออกว่า token ถูกปฏิเสธหรือสายหลุด — และเพราะ `refresh()` ทำงานเฉพาะตอน `onopen` มือถือที่ใช้ QR เก่าจึง**วนเชื่อมทุก 3 วิตลอดไป โดยไม่ขึ้น QR panel**

| อาการที่ตรวจได้ | ตีความ | ทำอะไร |
|---|---|---|
| `/health` = 401 | ปฏิเสธถาวร | ขึ้น QR panel · **หยุดวน** |
| อื่นๆ | สายหลุดชั่วคราว | ถอยหลัง 3 → 6 → 12 → 24 วิ (สูงสุด 24) |

ตรวจแล้ว: `stream_check` **14/14** (เพิ่ม 5) · `pool.py demo` **306/306** · `ctx_plane` **PASS** · `ui_check` **OK** · `prune_check` **13/13**

## 26. แผง ☰ — ค่าเดียว ต้องไม่ขัดกันเอง

ทุกบักในแผง ☰ มีรูปทรงเดียวกัน: **ค่าหนึ่งคุมสองอย่าง แล้วปล่อยให้มันขัดกัน** หน้าจอยังเรนเดอร์ เซิร์ฟเวอร์ยังตอบ 200 — ผิดแค่ *ความหมาย* ของสิ่งที่คุณกำลังดู

### เปลี่ยน "มุมมอง" แล้ว stream ไม่ตามไปด้วย

SSE ถือ identity ไว้ใน `as=` ของตัวเอง ตั้งแต่ตอนที่สร้าง URL · การเปลี่ยนมุมมองเรียก `refresh()` ซึ่งอ่าน**อดีต**ใหม่หนึ่งครั้ง แต่ไม่สร้าง stream ใหม่ → **บรรทัดถัดไป**ยังมาใต้ตัวกรองเก่า:

```
ก่อน:  setIdentity('hermes')  →  stream.url = /stream?n=200   (ไม่มี as= เลย)
หลัง:  setIdentity('hermes')  →  stream.url = /stream?n=200&as=hermes
```

หัวเว็บเขียน `hermes` แต่ feed ยังโชว์ทุกบรรทัดของ admin — และเพราะ feed คือสิ่งที่คน**อ่าน** ตัวที่ผิดจึงชนะ · `refresh()` แก้อดีต แต่ `listen()` คือสิ่งที่แก้อัตถัดไป

### ตัวเลือก "มุมมอง" โชว์คนละคนกับที่ใช้อยู่จริง

`#id-sel` ถูกสร้างใหม่จากแอปที่**อยู่ในหน้าต่างที่โหลดมา** — identity ที่ยังไม่มีบรรทัดไหนจะไม่อยู่ในตัวเลือก แล้ว select ตกลงไปที่ตัวแรก (`admin`) ทั้งที่ค่าจริงยังเป็นอีกคน

```
identity = 'zzz-not-in-window'   select โชว์ 'admin'   มีตัวเลือกนั้นไหม: ไม่มี
```

ตัวเลือกที่ขัดกับค่าที่มันเลือก แย่กว่าไม่มีตัวเลือก — เพราะตัวเลือกถัดไปถูกเทียบกับค่าที่ไม่เคยจริง

### อ่านทะเบียนไม่ผ่าน = ซ่อนทั้งกล่อง

เดิม `catch{regbox.style.display='none'}` ทำให้ *"ต่อเซิร์ฟเวอร์ไม่ได้"* กับ *"ยังไม่มีใคร register"* เหมือนกันเป๊ะ · ตอนนี้กล่องอยู่และบอกว่าเป็นอันไหน

### Escape ปิด modal แล้วไม่ทำอะไรต่อ

modal ระนาบเป็น `z-index:50` แผงเป็น `z-index:40` แต่มีแค่ modal ที่มีตัวจับ `Escape` → Escape ปิดอันบนสุด แล้วทิ้ง scrim ค้างไว้ กดได้อย่างเดียวคือแตะมัน · และตัวแผงเองไม่มีวิธีกดคีย์บอร์ดปิดเลย · ตอนนี้ตัวจับเดียวไล่ปิดจากบนลงล่าง**ตามลำดับชั้น** ไม่ใช่ตามใจ

`/flush` ได้วิธีเดียวกับช่องแชท — มันคือปุ่มเดียวที่ทำหน้าที่ตอบคำถามว่า *"ถึงคลาวด์หรือยัง"* จึงเงียบไม่ได้

### ตรวจแล้ว

`ui_check` เพิ่ม 4 invariants — และ**สองเวอร์ชันแรกผิดแบบสอนได้**: ครั้งแรกผ่านบนโค้ดที่พังเพราะคอมเมนต์ระหว่าง `identity=a;` กับ `listen(` ยาวเกินหน้าต่าง `{0,300}` · ครั้งที่สองก็ยังผ่าน เพราะ**คอมเมนต์เองมีคำว่า `listen()`** → ตอนนี้บังคับเป็น *คำสั่งจริง*

    ^\s*listen\s*\(\s*\)\s*;      ← ต้องเป็นบรรทัดคำสั่ง คอมเมนต์ตอบไม่ได้

ทดสอบด้วย 6 mutation ที่ย้อนบักกลับทีละตัว: **จับได้ทั้ง 6** baseline สะอาด

> เทสต์ที่ล้มไม่ได้ ไม่ใช่เทสต์ — ทั้งสองเวอร์ชันที่ล้มเหลวข้างบน ขึ้นเขียวบนโค้ดที่มันถูกเขียนมาปกป้องเอง

## 27. ระนาบ — popup ที่ตัดไม่ได้แล้ว และแว่นที่ไม่สะดุดอีก

### popup ถูกตัด = เป็นไปไม่ได้โดยโครงสร้าง

วัดบนเบรกพอยต์มือถือ (540×709):

```
#plane-canvaswrap   overflow:hidden · สูง 165px
#plane-pop          สูง 164px · top=4px → ล่างสุด 168px > 165px
```

และ**สูตร clamp แก้ไม่ได้**: `wr.height - popH - 10` = **-9** แล้ว `Math.max(4,·)` ดันกลับเข้าไปข้างใน

> **popup ที่สูงกว่ากล่องที่มันอยู่ในนั้น ยัดกลับเข้าไปไม่ได้** — ไม่มีเลขไหนแก้ได้ มีแต่เปลี่ยนกล่อง

ตอนนี้ popup กับ tooltip เป็น **`popover`** → อยู่ใน **top layer** ซึ่งหลุด `overflow:hidden` ได้โดยโครงสร้าง และวาดทับ/ถูกทับผิดอันไม่ได้ด้วย (นี่คืออีกครึ่งของเรื่องที่ตีกันใน §26)

การจัดตำแหน่งเทียบกับ **viewport** ไม่ใช่กล่องแคนวาส + `max-height:calc(100dvh - 24px)` กับ `overflow:auto` → clamp หาคำตอบได้เสมอ popup **เลื่อนได้** แทนที่จะถูกตัด · tooltip เดิม `white-space:nowrap` ทำกล่องกว้าง 350px บนแคนวาส 540px → ตอนนี้ขึ้นบรรทัดใหม่และ clamp กับ viewport

ตรวจแล้วบนมือถือ: **popup ล่างสุด 486px ทั้งที่กล่องจบที่ 462px** — ล้นออกนอกกล่องเดิมและ**เห็นครบ** รวมปุ่มปิด · tooltip ขอบขวา 534 ≤ 540

และเพราะ popup ยึดกับ **จุดบนแคนวาส** ไม่ใช่ยึดกล่อง → resize/scroll แล้วจุดอ้างอิงขยับ ตัวมันก็ถูกจัดใหม่ทั้งสองกรณี (เดิมจัดครั้งเดียวแล้วไม่แตะอีก)

### แว่นสะดุด เพราะสามอย่างซ้อนกันอยู่ทุกเฟรม

| | ก่อน | หลัง |
|---|---|---|
| วาดระนาบฐาน (plane mode) | 27.7 ms (สูงสุด 37.3) | **0.02 ms** |
| ตั้ง `canvas.width` ต่อ 30 ครั้ง | 30 | **0** |
| เฟรมลากแว่น | 12.8 ms | **2.6 ms** |
| ขั้นหมุนล้อซูม | 12.5 ms | **2.1 ms** |
| `pvKeep()` ต่อครั้ง | เดินทุกเส้น สูงสุด 4 รอบ/เฟรม | **0.013 ms** |

**1. backing store ถูกสร้างใหม่ทุกเฟรม** — `pcv.width=px*dpr` ทำให้แคนวาส realloc **และล้างทั้งผืน** ทุกครั้ง (วัดได้ 30 ครั้ง ต่อ 30 การวาด) ตอนนี้ตั้งเฉพาะเมื่อขนาดเปลี่ยนจริง

**2. เฟรมซูมวาดระนาบใหม่ทั้งผืน** — ระนาบโหมดเต็มวาด **10,131 เซลล์ใน 27.7ms** และแว่นวาดลงแคนวาสเดียวกัน → ทุกล้อหมุน/ทุกเฟรมลากจ่ายค่าระนาบทั้งผืนก่อน ระนาบฐานตอนนี้เรนเดอร์ครั้งเดียวลง offscreen แล้ว blit

โดยคีย์แคชคือ input ที่มันอ่านจริง จับด้วย **identity ของ object** (cells/bonds/sights ถูกแทนที่ทั้งก้อน ไม่เคยแก้ในที่) → แคชค้างไม่ใช่ความเสี่ยงที่ต้องให้เหตุผล มันคือคีย์ไม่ตรง

`PV.origin` อยู่ในคีย์เพราะในโหมดหน้าต่าง มันย้ายทุกเซลล์**โดยไม่แตะ `PV.cells` เลย** — "กรอบเลื่อนตามเมื่อแว่นชนขอบ" (§24) จะทิ้งระนาบฐานค้างไว้ข้างหลัง กลายเป็นบักที่ดูเหมือน artefact แล้วไปโทษแว่น

**3. อาเรย์เส้นถูกสร้างใหม่ทุกสำเนาแว่น** — `pvGraphEdges()` สร้าง object ใหม่ **13,572 ตัวต่อครั้ง** และ `pvLensOne` เรียกมันทุกสำเนาที่วนรอบ (สูงสุด 4 รอบ/เฟรม) · `pvDrawnEdges()` จัดอันดับ degree ใหม่ทุกครั้ง · `pvKeep()` สร้าง adjacency map ทุกครั้ง → memoise ทั้งสามตัว 12.8ms → 2.6ms

### ยังเหลืออะไร

`devicePixelRatio` เป็นเศษ (วัดได้ 1.232) × ขนาด css จำนวนเต็ม เดิมได้ backing store **ไม่ใช่จำนวนเต็ม** → ตอนนี้ `bw=Math.round(px*dpr)` และ transform เป็น `bw/px` ขนาดกับสเกลจึงตรงกันโดยโครงสร้าง

**ที่ยังไม่หาย:** กริดเซลล์ยังตกบน device pixel เศษ (2 css px × 1.232 = 2.465) ขอบเซลล์จึงยังนุ่มเล็กน้อยที่สเกลระนาบ · การ align backing store แก้ความไม่ตรงกันระหว่าง *ขนาดแคนวาส* กับ *สเกล* ไม่ได้ทำให้ *เรขาคณิต* ลงตัว — นั่นต้องเลือก `step` เป็น device px แล้วรับ css step เป็นทศนิยม ซึ่งแก้ `pstep()` ตัวที่ทุกการวางตำแหน่งถาม (§10.5) จึงควรทำแบบตั้งใจแล้ววัดผล ไม่ใช่ผลข้างเคียง

ป้ายของแถบกว้าง 349px และแถวแบบ wrap ตัดสินใจจาก**ผลรวม basis** ป้ายที่กว้างเท่าเนื้อหาจึง**ดันสไลเดอร์ตกแถวเอง** → กำหนด basis คงที่ + ellipsis ของเต็มอยู่ใน tooltip (กฎเดียวกับข้อ 1)

### 3. ตัวคุม 14 ตัว ตะโกนพร้อมกัน

### 4. 🔍 ชุดซูม — ใหญ่ อยู่ที่เดิม และหยุดที่ที่แบบจำลองหยุด

ปุ่ม 46px วางทับบนแคนวาส · ตัวเลขระดับอยู่**ระหว่าง `+` กับ `−`** เพราะมันคือผลตอบกลับของสองปุ่มนั้น

สองกติกาที่ทำให้มันเป็นเครื่องมือ ไม่ใช่ปุ่มสามปุ่ม:

- **หยุดที่ที่แบบจำลองหยุด** — `+` ดับที่สเกลจริง (ที่เดียวกับที่ §24 สัญญาไว้) และ `−` ดับที่ ×1 ปุ่ม `+` ที่ยังทำงานต่อ ณ จุดนั้น = UI ขัดกับแบบจำลอง
- **⟲ ย้อน ทั้งสองแบบของการซูม** — ทั้ง ×ของแว่น **และ** การที่มุมมองถูกบีบเป็นบล็อก/หน้าต่าง — แล้ววางแว่นกลับที่จุดที่เลือก จึงใช้แทน "ลากหายไปแล้ว" ได้ด้วย · ความต่างระหว่าง "ซูมเท่าไร" กับ "ดูแถวไหน" เป็นความต่างของ**เรา** ไม่ใช่ของคนอ่าน สองปุ่มรีเซ็ตจะทำให้เขาต้องเดาว่าจะเอาแบบไหน

บนมือถือชุดซูม**นอนลง**: คอลัมน์สูง 170px ข้างแคนวาส 235px คือ **72% ของความสูงแคนวาส** — ตัวคุมที่กลบสิ่งที่มันคุม → เป็นแถวนอนสูง 60px = 25%

### error: สายไฟเป็นอังกฤษ และแปลที่จุดที่คนอ่าน

`error` คือสัญญััญญาระหว่าง API — `pool.py` · CLI · `stream_check` และ agent
ที่โพสต์ JSON อ่านมันหมด และ `stream_check` **assert ตัวข้อความ** ถ้าเขียนเป็นไทย
ก็เท่ากับแปลศัพท์ของเครื่องให้เครื่องตัวอื่น

ที่ผิดคือ **เบราว์เซอร์พิมพ์มันออกมาตรง ๆ** จึงแก้แบบเป็นชั้น ไม่ใช่ทั้งระบบ:

* สายไฟไม่ขยับ — `{"error": …, "howto": …}` เหมือนเดิมทุกไบต์
* เพิ่ม `sayError(r, st)` — จับคู่สาเหตุที่รู้จักเป็นไทย → ตารางรหัส HTTP → ประโยคกลาง
* `sayRaw(r, st)` เก็บข้อความเดิมไว้ และ `toast(text, detail)` เก็บมันลง **tooltip**

วัดจากหน้าจริง:

| สายไฟว่า | toast บอก | tooltip เก็บ |
|---|---|---|
| `zzz not registered — POST /register first` | แอป “zzz” ยังไม่ได้ลงทะเบียนไว้กับพูล — ลงทะเบียนก่อนจึงจะเขียนได้ | ข้อความจากเซิร์ฟเวอร์: … · HTTP 403 |
| `body must be a JSON object` | ข้อมูลที่ส่งไปอ่านไม่ได้ — ข้อความนี้ยังไม่ถูกบันทึก | … · HTTP 400 |
| `token required — open /qr from the server screen` | ยังไม่ได้เข้าสู่ระบบ — สแกน QR ใหม่จากหน้าจอเซิร์ฟเวอร์ | … · HTTP 401 |
| `no ctx index yet — …` | ยังไม่มีข้อมูลความจำกลาง — ต้องรันตัวสแกนที่เซิร์ฟเวอร์ก่อน | … · HTTP 503 |
| อะไรที่ไม่รู้จัก + HTTP 500 | เซิร์ฟเวอร์ทำงานผิดพลาด — ลองอีกครั้ง ถ้ายังไม่หายให้ดู log | — |

**ลำดับสำคัญ:** สาเหตุที่รู้จัก ชนะ รหัส HTTP ชนะ ประโยคกลาง · ลำดับนี้ทำให้ error
ที่ไม่รู้จักแต่สถานะรู้ กลายเป็นประโยคของสถานะ — `weird-message` + 400 ได้ประโยค 400
ซึ่งมีประโยชน์กว่าคำทักทายที่เซิร์ฟเวอร์บังเอิญส่งมา

`send()` ต้องเลิกทิ้งรหัสสถานะด้วย: `fetch(…).then(r=>r.json())` ทิ้งมันไป ทำให้โค้ด
ที่บอกว่า *ควรลองอีกไหม* ไม่เคยไปถึงประโยคที่บอกว่า *ทำไม* ตอนนี้เก็บ `Response` ไว้
และ body ที่ไม่ใช่ JSON ก็ถูกจับ ไม่กลายเป็น rejection ลอย

## 30. `error_check.py` — error ทุกอันมีประโยคของตัวเอง

เพราะรายการแปลเป็น **ลิสต์** และลิสต์คือสิ่งที่ค้างตามหลัง — `ui_check` มองไม่เห็น
เพราะมันอ่านแต่ dashboard ไม่เคยถามเซิร์ฟเวอร์ · `pool.py demo` ก็ **306/306 ผ่านหมด**
เพราะฝั่งเซิร์ฟเวอร์ถูกเสมอ · สิ่งที่ต้องตรวจคือ **รอยต่อของสองไฟล์**

### ทำไมต้องยิงจริง · และทำไมแค่ยิงจริงไม่พอ

| แหล่ง | เก็บอะไร | ทำไม |
|---|---|---|
| **LIVE** | ยิง junk 39 ครั้ง ทุก endpoint ทุกวิธีที่ผิด | นี่คือความจริงบนสายไฟ |
| **SOURCE** | `{"error": …}` ทุกอันใน `pool_server.py` (อ่านด้วย `ast`) | 401 สองอันยิงจาก loopback ไม่ได้ (`_authorized` เชื่อ 127.0.0.1) — **ยิงไม่ได้ ≠ ไม่ต้องตรวจ** |
| **DASHBOARD** | สคริปต์แปล ที่ตัดออกจากหน้าเว็บไปรันใน node | เทสต์กับแอปจะได้เถียงกันเรื่อง pattern ไม่ได้ |

แล้วแยกทุก error เป็นสามชั้น **ด้วยรายการ pattern ของแอปเอง**:

| ชั้น | ความหมาย |
|---|---|
| **NAMED** | pattern จับได้ → ประโยคบอกว่า **เกิดอะไรขึ้นจริง** |
| **STATUS** | pattern ไม่จับ แต่รหัสสถานะอยู่ในตาราง — จริง แต่กลาง ๆ |
| **GENERIC** | ไม่จับอะไรเลย — คนอ่านไม่รู้สาเหตุ |

ผ่านเมื่อ **ทุกอันเป็น NAMED และไม่มี GENERIC เลย** · ช่องว่างระหว่าง NAMED กับ STATUS
คือหัวใจ: `text required` กับ `?n=<int> required` ต่างเป็น 400 ทั้งคู่ และ
"ส่งข้อมูลไปไม่ครบหรือรูปแบบไม่ถูกต้อง" ไม่ได้บอกอะไรที่คนอ่านยังไม่รู้อยู่แล้ว

```bash
python error_check.py          # รันเซิร์ฟเวอร์บน log ชั่วคราว ตรวจ แล้วเก็บกวาด
python error_check.py --gaps   # ดูรายการที่เป็น STATUS-only ด้วย
```

### รอบแรกเจออะไร — บั๊กจริง

รอบแรกล้ม 3 จาก 6 ข้อ และหนึ่งในนั้นคือบั๊กชนิดเดียวกับ §12 ที่แก้ไปแล้ว **แต่อยู่อีกฝั่งของโปรโตคอล**:

```
FAIL every-probe-answers       no response at all: tail-n-text -> status=0;
                               view-n-text, stream-n-text, curator-n-text,
                               curator-hide-text, curator-at-text
FAIL every-error-is-named      8 อันตกไปที่ประโยคของรหัสสถานะ
FAIL no-traceback-on-bad-params  6650 bytes of stderr
```

`int(qs.get("n")[0])` ไม่มี guard ใน `/tail` · `/view` · `/stream` และ `/curator`
(อีกสองที่สำหรับ `hide`/`at`) → `?n=abc` โยน exception ทะลุ `do_GET` →
**ลูกค้าไม่ได้รับคำตอบเลย** (curl รายงาน `http=000`) และ stderr ได้ traceback

กติกาของ §12 — *คำขอที่ล้มเงียบ กับเซิร์ฟเวอร์ที่ตายไปแล้ว หน้าตาเหมือนกันเป๊ะ

ตอนนี้ตอบครบทั้งห้า ผ่าน helper ตัวเดียว:

```

/curator?n=abc       http=400  {"error": "?n=<int> required"}

```

และ 8 error ที่ไม่มีประโยคก็ได้ประโยคของตัวเอง:

## 31. ผัง 12×12 — เจอบั๊กจริง และสองท่าบนจอสัมผัส

### 31.1 ผัง 12×12 เคยวาดบล็อกทั้ง 144 ตัวทับกันในแถวเดียว

วัดจากหน้าเว็บจริง ตอนที่ยังไม่ได้แก้:

```
Object.keys(PV.cells).length                          144
new Set(keys.map(k => pvXY(k).join(','))).size         12
ช่องที่ pvRkeyAt(x,y) ไม่ใชุ่มุมบล็อก                  132 / 144
```

**144 บล็อก แต่วาดได้ 12 ตำแหน่ง** — เพราะ `pvDerive` ตั้งคีย์ของการรวมกลุ่มด้วย
**ลำดับบล็อก** (`by*12+bx`) แต่ `pvXY` อ่านเป็น**ที่อยู่ของช่อง** (`(rk%144)/12`,
`rk/144/12`) → ทุกบล็อกถูกวาดที่แถว 0 ทับกัน 12 ชั้น ส่วนเส้นเชื่อมรอบ ๆ (ซึ่งใช้
ที่อยู่จริง) วางถูกตำแหน่ง · ภาพที่เห็นคือแถบสีเขียวแถวเดียวบนกองเส้น

และเพราะ heat map **ไม่มีป้ายชื่อ** อาการเดียวที่คนดูรู้คือ *“แผนที่นี้ดูงง”*

ความแยกสองที่เดียวกันนี้ยังหลอกบนจออีกสามจุด ซึ่งแก้พร้อมกันในครั้งเดียว:

| สิ่งที่เคยผิด | เพราะ |
|---|---|
| สี “ใครเขียน / ล่าสุดเมื่อไร” | อ่าน `cellApp[blockIndex]` = ช่องอื่นคนละช่อง |
| รัศมี (hop) จางทุกช่อง | `keep.has(blockIndex)` เทียบกับชุดของที่อยู่ช่อง → ไม่มีวันตรง |
| แว่นขยายเห็นผังว่าง | ถาม `PV.cells[ที่อยู่ช่อง]` กับแผนที่ที่คีย์เป็นบล็อก → อ่านว่า “0 line” เหนือบล็อกที่มี 2,228 |

การแก้ไม่ใช่ “ปรับสูตรใน `pvXY`” แต่คือ**ตัดที่อยู่ชุดที่สองออก**: บล็อกถูกคีย์ด้วย
**ที่อยู่แรกของตัวเอง** (`(by*12)*144 + bx*12`) — ซึ่งเป็นค่าที่ `pvRkeyAt`
ส่งกลับและ `pvXY` รับอยู่แล้ว → แก้บรรทัดเดียว ถูกพร้อมกันสี่จุด

```
new Set(pvXY(k)).size   144      ภาพกับคลิกขัดกัน   0 / 144 ช่อง
```

`pvValAt(rk)` ถูกเพิ่มเป็นที่เดียวที่สองสเกลต้องมาเจอกัน (แว่นถามค่า *ที่ช่อง*
แต่บนผังบล็อกเก็บเป็นบล็อก → ช่องยืมค่าของบล็อกที่ครอบมัน)

### 31.2 ลากเพื่อเลื่อนผังบล็อก

ผัง 12×12 แสดงทั้งระนาบอยู่แล้ว ลากจึงไม่ได้เปิดที่ใหม่ — แต่ระนาบนี้เป็น**วงแหวน
ทอรัส** การเลื่อนขอบคือตำแหน่งมองจริง: ภาพไถลตามนิ้วและวนกลับเมื่อครบ 12 บล็อก
(วัดแล้ว: ลากขวา 3 ล่าง 1 → `bOrig {x:9, y:11}` และภาพตรงกับการหมุนทั้งผัง
**144/144 ช่อง**)

แถบสถานะ**บอกก่อนลอง** เพราะคำตอบที่ซื่อสัตย์ไม่ตรงกับที่ท่าทางสื่อ:

```

```

### 31.3 บีบสองนิ้ว = ซูมเข้า/ออก

มือถือไม่มีล้อ และปุ่ม `±` เป็นของ**แว่นขยาย** — ท่าบนแผนที่ที่ทุกคนรู้จักคือ
“ดูมากเท่าไร” จึงเดินบนบันไดของขอบเขต และใช้ห้าขนาดที่ตัวเลือก “กรอบเลื่อน”
มีเท่านั้น:

```
   12  ->  24  ->  36  ->  48  ->  72  ->  blocks  ->  plane
  (เข้า)                                   (ออก)
```

บีบออกจากผังบล็อก = เปิดกรอบที่บล็อกใต้กึ่งกลางนิ้ว (วัดได้: บีบที่บล็อก (6,8)
→ `win=12` และ origin `{72,96}` = บล็อกนั้น) · บีบเข้าจากกรอบ 12×12 → 24 → 36
→ 48 → 72 → ผังบล็อก → ทั้งระนาบ แล้ว**หยุดพร้อมบอกว่าหยุด**: ซูมออกกว่านี้ไม่มี
อะไรอยู่ข้างนอก และกรอบเล็กกว่านี้ไม่มี (ใช้แว่นแทน)

สิ่งที่เพิ่มในฝั่งสัมผัสมีแต่การนับนิ้ว ซึ่งพลาดแล้ว**มองไม่เห็น**:

* นิ้วที่สองลง → ทิ้งการลากของนิ้วแรก (ไม่งั้นกรอบเลื่อนสองเท่าต่อเฟรม)
* บีบเสร็จ → กลืนคลิก (ไม่่งั้นยกสองนิ้วแล้วเปิดช่องที่นิ้ววางอยู่)
* pointercancel → ปล่อยกรอบที่ค้างอยู่

### 31.4 เทสต์ที่ใหม่: รันโค้ด ไม่ใช่จับ regex

invariant เดิมเป็น regex — *“pvXY อ้าง PV.bOrig, pvRkeyAt เรียก pvBlockKey”*

ที่อยู่ยังผิด (`key*12` คือคอลัมน์ของบล็อกแต่แถวผิด) · **รูปร่างไม่เห็นเลขคณิต**

ส่งให้ node พร้อม `PV` จำลอง แล้วยืนยันว่าตรงกัน 15 ตำแหน่งขอบ × 144 ช่อง +
144 บล็อก × 3 ช่อง


## 32. โหมดแนะนำ 3 ขั้น — โผล่ครั้งแรก ปิดได้ จำไว้ใน localStorage

| 1 · ค้นข้อความ | พิมพ์ในช่อง `กรองข้อความ…` (ค้นด้วยรหัสยาวก็เจอ) | พิมพ์ในช่องค้นจริง |
| 2 · ดูบนแผนที่ | กด `▦ แผนที่` — ทุกบรรทัดมีที่อยู่ กดช่องเพื่อเปิดดู | กดปุ่มแผนที่จริง |
| 3 · ลากดูเส้นเชื่อม | ลาก = เลื่อน · เส้น = บันทึกที่อ้างถึงกัน · บีบสองนิ้ว = ซูม | ลากบนแผนที่จริง |

กติกาที่ทำให้มันเป็นทัวร์ ไม่ใช่การรบกวน:

* **โผล่ครั้งเดียว** — ปิดด้วย `ข้าม` / `เริ่มใช้งาน` / คลิกพื้นหลัง → เขียน `pool_tour_done` ลง localStorage → **ไม่โผล่อีกตลอด** (รีเฟรชก็เงียบ)
* **กลับมาดูใหม่ได้ตลอด** — `แนะนำการใช้งาน` มุมขวาล่าง (ข้าง `สำเนาเดี๋ยวนี้`)
* **ปุ่มถัดไปยังอยู่** สำหรับคนที่อยากอ่านไปเรื่อย ๆ แต่การทำจริงเร็วกว่า
| `⟲` | กลับทั้งระนาบ + รีเซ็ตแว่น + คืนขอบผัง |
